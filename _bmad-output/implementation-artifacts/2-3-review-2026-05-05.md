## Summary

This story is in much better shape than 2.2. The contract is clean: a single `POST /v1/fingerprint/:jobId/confirm`, a shared `applyFingerprintConfirmEdits` helper exported from `@grc/types`, a transactional UPDATE + audit‑log insert, and a re‑validation step against `fingerprintInferencePayloadSchema` so a malicious or buggy client can't slip a corrupt payload past Zod into the tenant store. Several of the test/lifecycle gaps I flagged on 2.2 were also fixed in‑pass (job‑outcome ref, `submit()` teardown, polling cap, sources popover Escape handler), and the integration test file genuinely exercises the confirm path end‑to‑end.

Two things keep me from "approve":

1. **Audit‑log IP attribution is spoofable.** The route reads `X-Forwarded-For` directly from the raw header instead of using `request.ip` (which respects Fastify's `trustProxy` config). Behind any reverse proxy, a client can set `X-Forwarded-For: 1.2.3.4` and that value will land in the append‑only `platform_audit_logs.ip_address`. For the **first** thing the system records as an immutable security event, that's the wrong default.
2. **Bulk removals can produce a Zod‑invalid payload, and the user is left with a generic error.** A user can remove every `regulatoryObligations` (or `businessProcesses`, or `riskDomains`) line in bulk‑edit mode; the merge helper happily produces empty arrays, the server's re‑validation throws against `.min(1)`, and the client surfaces the route's terse "Edits would produce an invalid fingerprint payload…" message with no path forward except guessing which list is empty. Either guard at the UI layer (block the last × per category) or surface a structured error the client can map to a per‑category message.

A handful of smaller correctness/UX/test items follow.

**Verdict: Request Changes** — the IP attribution issue is small to fix and worth getting right before this lands; the empty‑list UX is a real onboarding dead‑end. Everything else is landable as follow‑ups.

## What Looks Good

- **Single source of truth for the merge contract.** `applyFingerprintConfirmEdits` lives in `@grc/types`, is consumed by both the server route and (implicitly via line ids) the client — no duplication, and the server re‑validates with Zod after merge so the type system isn't the only line of defense.
- **State machine is explicit.** The route distinguishes `404`, `409 ALREADY_COMMITTED`, `400 INVALID_STATE`, and `400 VALIDATION_ERROR` instead of returning 400 for everything. Makes downstream clients (and future logs) tractable.
- **Concurrency is handled correctly.** `UPDATE … WHERE status = 'pending_review' RETURNING job_id` + the empty‑rows check inside the `$transaction` callback gives single‑confirm semantics even under concurrent requests, and the audit insert is in the same transaction so a partial commit can't ship a bare audit row.
- **Tenant safety is consistent with 2.1/2.2.** Same `${tenantId}.fingerprint.` prefix guard, same `requireTier("starter") + requireRole("ControlOwner")`, raw SQL scoped to `request.tenant.schemaName`.
- **Schema alignment is real.** `confirmed_at`, `confidence_scores`, `industry`, and the `committed` status check‑constraint all exist in `tenant-template.sql`. The `confidence_scores` JSON shape matches what the worker writes on `pending_review` (no regression).
- **2.2 review carry‑forward is honored.** `jobOutcomeRef` gates `onerror` polling, `submit()` tears down `EventSource` and poll, polling has a max attempt cap (`POLL_MAX_ATTEMPTS = 60`), the popover now closes on Escape and outside‑click, the stagger constant is centralized — all items I flagged on 2.2 landed.
- **Synthetic integrations line is correctly routed away from server state.** UI lets the user "edit" / "remove" it for visual closure; merge helper ignores it; audit and stored data don't carry UI artifacts.

## Verdict

**Request Changes.** Two real issues — IP spoofing into the immutable audit log, and the empty‑list UX dead‑end — should land before this is merged. Both are small. Test gaps for the unhappy state‑machine branches and the bulk‑remove validation path are also worth closing while the context is fresh. Everything else is suggestions.

### Suggested follow‑ups (in order)

1. Switch the audit IP source to `request.ip` and document the proxy expectation.
2. Block the last × per required category in the client (or return structured `REQUIRED_LIST_EMPTY` with `category` and map it to per‑list copy).
3. Treat `409 ALREADY_COMMITTED` as a navigate‑forward.
4. Symmetric `edited[id]` reconciliation in bulk‑edit toggle (and prefer `delete` over `false` for parity with `overrides`).
5. Disable editor controls while `confirmBusy`.
6. Replace `JSON.parse(JSON.stringify(...))` with `structuredClone`.
7. Forward Zod `error.flatten()` in the post‑merge `VALIDATION_ERROR` 400.
8. Tests: `INVALID_STATE` (queued/failed), `DATA_CORRUPT`, oversized body, post‑merge VALIDATION_ERROR, client `409` UX, audit‑log `toHaveBeenCalledWith` shape, end‑to‑end overrides+removals body shape.
9. Add an `info` log on successful confirm with `{ jobId, tenantId, userId, overridesCount, removedCount }`.
10. Confirm `/integrations` and `/dashboard` resolve to at least an empty state to avoid linking the user to 404s.
