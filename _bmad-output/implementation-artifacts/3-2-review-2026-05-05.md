## Summary

The dashboard shell is in: a Redis‑cached read model endpoint, a TanStack Query client with 30 s `staleTime`/`refetchInterval`, an SSE endpoint on `tenant:{tenantId}:control-health` wired into `EventSource`, an inline summary bar + 8‑card grid + right‑side action feed + side‑panel "Fix now". The 3.1 panel pattern (translate animation, `aria-modal`, hand‑rolled focus trap, `openerRef` restoration, reduced‑motion support) was reused — that's the right move.

But there are four real defects that compromise the story as written:

1. **The Audit Director — the persona this story is written for — cannot read the dashboard.** `dashboardPreHandlers = [requireTier("starter"), requireRole("OrgAdmin")]`. `ROLE_SATISFIES["AuditDirector"]` is `["AuditDirector", "ControlOwner", "ReadOnly"]` — does **not** include `OrgAdmin`. So an Audit Director hitting `GET /v1/dashboard` gets a 403. Meanwhile `controlHealthStreamPreHandlers = [..., requireRole("AuditDirector")]` admits the persona to the SSE stream. The two role gates are inverted relative to the story.
2. **SSE updates can take up to 30 s to reflect.** On `control.degraded`/`control.passed`, the client calls `qc.invalidateQueries({ queryKey: ["dashboard-read-model"] })` — which triggers a refetch — but the API serves whatever is in the per‑tenant Redis cache (`grc:dashboard:{tenantId}`, 30 s TTL) and there is no cache‑busting on the publish side. AC #3 says "the affected ControlCard re‑renders with the new status within 5 seconds." With a populated cache, the dashboard re‑renders the same stale data the cache already had.
3. **The "ECGPulse 30‑day sparkline pre‑computed server‑side" is fake.** `dashboard.ts` L107: `sparkline30d: Array.from({ length: 30 }).map(() => Math.round(passRatePct))` — thirty copies of *the current pass rate*. The dev's comment even concedes "Placeholder until we have real 30‑day history persisted server‑side." AC #2 calls for a real series. The UI further degrades this to a single text line ("30d trend: 75%") with no actual sparkline component (`ECGPulse` is named in the spec; not implemented).
4. **SSE pub/sub message handler can fire before `reply.hijack()` / headers are written.** `stream.ts` L153 attaches `sub.on("message", onMessage)` *before* `await sub.subscribe(channel)` resolves, and only then calls `reply.hijack()` + `reply.raw.writeHead(...)`. Redis can deliver a queued message between the listener attaching and the response being hijacked, in which case `reply.raw.write(...)` runs against an un‑hijacked reply with no headers. Best case: the write is dropped. Worst case: throw (`headersSent` violation depending on Fastify version) and the SSE never opens.

A handful of smaller items follow.

**Verdict: Request Changes.** All four are addressable; #1 is one line, #2 is a publish‑side `redis.del`, #3 is either real data or a clearer placeholder, #4 is reordering five lines.

> **Test execution note.** `pnpm -r test` was not independently run in this review's sandbox (`@rollup/rollup-linux-arm64-gnu` native binding is absent under the review VM). Test logic was verified by reading the suite vs. implementation; the dev's claim of green is plausible — but the suite does not exercise the AuditDirector persona, the SSE→cache‑bust path, or the cache‑hit content, so "green" doesn't yet mean "covered."

## What Looks Good

- **Tenant‑scoped pub/sub channel name is correct.** `tenant:{tenantId}:control-health` matches the architecture envelope, and the channel name is constructed from `request.tenant.tenantId` — never trusting client params.
- **Server envelope discipline holds.** `{ data: ... }` on success, `{ error: { code, message } }` on failure — including the cache‑hit path. The `ensureTenantSchemaNameOrReply` helper from 2.6 is reused here, keeping the regex defense centralized.
- **TanStack Query staleness model is honest.** `staleTime: 30_000`, `refetchInterval: 30_000`, plus SSE invalidation. Fixing the Redis cache‑bust path (Critical #2) is the only thing standing between this and a real "no full‑page loading on revisit" experience.
- **SSE cleanup is genuine.** `request.raw.on("close")` fires `clearInterval(heartbeat)`, `removeListener`, `unsubscribe(channel)`, `quit()`. No interval leaks per request. Same on the client: `useEffect` returns a cleanup that removes listeners and closes `EventSource`.
- **Reduced motion is respected end‑to‑end.** `addEventListener('change', …)` subscription pattern matches the 3.1 fix (carry‑forward 2.6 #6 closed). Panel honors `panelReducedMotion` for both open and close paths.
- **Existing job stream is preserved.** `streamRoutes` still registers `/v1/stream/jobs/:jobId` with its original `ControlOwner` gate; `server.ts` registers both. Story Task 3's "do not break fingerprint streaming" goal is met — modulo Critical #4's race, which was actually pre‑existing in this file.
- **Onboarding affordances on `/dashboard` are intact.** `DashboardOnboardingActions` still mounts above `DashboardClient`; the dev didn't tear out the 2.5 onboarding path while shipping 3.2.
- **Dashboard test stubs `EventSource` correctly.** The `vi.stubGlobal("EventSource", …)` pattern is the right way to keep the unit test isolated; once Critical #2 is fixed and the suggestions in #22 land, this file becomes the canonical SSE‑in‑a‑unit‑test pattern for the codebase.
- **Counts aggregation is correct.** `pass`/`auto` → passing, `warn` → attention, `fail` → failing. The test locks `1, 1, 1` for a 3‑row fixture. The `auto` mapping matches the 3.1 `statusVariantFromApi` choice — internal consistency.

## Verdict

**Request Changes.** The persona‑gate inversion (Critical #1) and the cache‑staleness vs SSE conflict (Critical #2) are functional defects against the story; the sparkline (Critical #3) is below the AC bar; the SSE race (Critical #4) is a latent correctness bug duplicated from the existing jobs handler. After those, the placeholder padding (#5), missing component extractions (#6), un‑collapsible fail items (#12), and untouched "Assign" buttons (#11) are the visible polish gaps.

### Suggested follow‑ups (in order)

1. Change `dashboardPreHandlers` to `requireRole("AuditDirector")`. Add an AuditDirector 200 test and a ControlOwner 403 test (mirrors `frameworks.test.ts` patterns).
2. Make whatever process publishes `control.degraded`/`control.passed` (today: not yet wired — but the route is) also do `redis.del(grc:dashboard:{tenantId})`. Add a route test that pre‑seeds the cache and asserts the next read recomputes after a simulated event.
3. Decide on the 30‑day history model: either land a `domain_pass_history` aggregation (story 3.x?) or return `sparkline30d: null` and have the UI render an honest "history coming soon" state. Either way, replace the synthetic flat array.
4. Reorder SSE handlers: `reply.hijack()` + `writeHead` first, *then* `sub.on("message", onMessage)`, *then* `subscribe`. Apply to both `/v1/stream/jobs/:jobId` and `/v1/stream/control-health`. Factor the boilerplate into a helper while you're there.
5. Replace `fixedDomains` padding with a backend contract that emits exactly the canonical 8 domains, OR render only the real ones.
6. Promote `HealthSummaryMetric`, `ControlCard`, `ECGPulse` (real SVG) to `packages/ui` with Storybook stories per UX spec §1138.
7. Fix `expanded = open || severity === "fail"` to `useState(() => item.severity === "fail")`. Wire or remove the "Assign" buttons.
8. Tighten the `aria-live` announcement region — scope to a delta sentence instead of the whole summary grid.
9. Land 3.1 carry‑forwards (`@grc/types` schema, row a11y, PATCH body) — they now affect 3.2 via `DashboardOnboardingActions`.
10. Strengthen tests: AuditDirector 200, ControlOwner 403, SSE event → invalidation, cache hit content assertion, SSE cleanup on unmount, message‑before‑hijack queue/drop.
